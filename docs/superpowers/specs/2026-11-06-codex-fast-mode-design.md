用户希望继续在 DSH 中使用 ChatGPT 套餐模型，并能选择真正的 Fast 服务档位，而不是通过降低推理强度来代替。

## 方案比较

### A. Web 设置控件 + profile 配置项（用户已确认）

在已有 OpenAI Codex 设置页增加 Standard / Fast 选择，保存到对应 DSH profile 的插件配置；无 Web 的使用方式也能通过配置项选择。

优点：符合用户当前 Web 使用习惯，有明确的恢复 Standard 的入口，不需要修改 DSH 核心或制造伪模型名称。代价：除了请求适配器，还需要修改设置页、受保护的设置路由及配置持久化测试。

### B. 仅提供配置项

只在插件配置中增加服务档位，通过配置文件切换。

优点：实现较少，TUI 与 Web 后端都能使用。代价：Web 用户不能直接在设置页切换，需要手动修改配置。

不采用硬编码全部请求为 Fast：会在用户不知情时提高额度消耗，且不便恢复 Standard。也不引入 `xxx-fast` 伪模型来混淆模型与服务档位。

## 推荐设计

### 1. 先整理兼容基线

- 保留 GitHub 上游提交历史，用独立提交同步 npm 官方发布的干净 0.3.1 源码。
- 不从当前运行目录整包复制，不导入登录信息、token、机器路径或运行缓存。
- 保留并调整上游测试，确保 0.3.1 新增的登录与额度功能没有倒退。npm 发布包不包含测试和构建脚本，不能整目录替换仓库；需要补齐发布版脚本引用的 companion-auth 测试，并调整旧版额度行为断言。
- 将本机已有的非法 `ultra` 推理档位过滤作为独立、带测试的兼容修复保留，而不是混入发布版同步。

### 2. 配置与设置页

推荐的使用效果：

```text
设置 → OpenAI Codex

服务档位： [ Standard ▾ ]
             Standard
             Fast

Fast 会提高套餐额度或付费额度的消耗；与推理强度独立。
```

- 默认 Standard，现有安装未显式开启 Fast 时不主动请求 Fast。
- 选择对当前 profile 中该插件的后续请求生效，包括工具后续轮次、历史压缩等；不改变其他 provider，也不修改已发送的请求。
- 使用 DSH 的插件配置持久化机制，不把服务档位写入 OAuth 凭据。
- 设置保存失败必须明确报告，不能让界面假装已经保存。
- 新增设置写操作沿用现有 localhost、Origin、HTTP method 校验，严格校验服务档位值。

### 3. 请求行为与限制

- 开启 Fast 后发送 `service_tier: "fast"`；模型 ID、推理强度、工具、历史和凭据路由保持原样。
- 不支持或无资格时明确呈现服务端错误，不偷偷改用 API Key、不静默重发 Standard。
- 界面表示“请求的服务档位”，不能把已选 Fast 宣称为服务端一定使用了 Fast。
- 不加入 Ultrafast、不改额度计算规则，不借机重构 OAuth 流程。

### 4. 测试与验证

- 先编写失败测试，再实现服务档位配置、请求映射和受保护的设置路由。
- 覆盖默认行为、Fast、切回 Standard、非法参数、配置持久化失败，以及与推理强度独立的行为。
- 运行完整自动化测试、Web bundle 构建和安装包内容检查。
- 自动化阶段只使用 mock，不消耗真实 ChatGPT 模型额度。
- 未经用户另外同意，不进行真实模型请求；因此自动化通过不等于已经验证账户具备 Fast 资格。
